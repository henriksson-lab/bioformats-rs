## Corrected implementation

LEI (`LeicaReader.java` → `src/formats/gpl/leica.rs`):

- OME projection covers every logical series and preserves selection. Each
  image links to its own Instrument, Objective, Detector and Filter identities.
- Sparse instrument indices are retained without the previous index-64 cap.
- Detector offsets preserve zero and negative values. Voltage is projected onto
  the Detector, matching `setDetectorVoltage`; the former extra DetectorSettings
  offset/voltage and detector Model fields were removed from the LEI projection
  because Java does not set them there.
- Instrument SAFEARRAY blocks retain source ordering. Detectors are emitted and
  cleared per block, including active detectors beyond the channel count.
- Emission-filter references and wavelength limits respect active-channel state
  at the time of each record and preserve physical filter IDs.
- Objective correction and immersion use the Java enum-handler vocabulary,
  including historical aliases and Leica's reversed-token correction.
- Instrument `dblVoxelX`, `dblVoxelY`, `dblStepSize` override dimension-derived
  physical sizes, as in Java. Zero pinhole defaults and integer time-increment
  gating match the corresponding metadata calls.
- Plane exposure is emitted only for timestamped planes, as in Java initFile.

LMS (`MetadataStoreInitializer.java` and LMS metadata extractor):

- Objective serial number and settings refractive index now reach structured OME.
- Detector Zoom, Microscope Type, and Laser Type/LaserMedium are represented and
  populated through the shared OME model.
- Java-backed hardware extraction no longer invents Detector Gain or Laser Model
  values. Explicit hardware fields in the existing Rust-only raw-metadata
  extension remain available.

## Stale audit claim removed from the implementation backlog

The claim that Java XLEF supports compressed Memory or arbitrary multiple
Memory/Storage raw-image declarations is not supported by its source.
`XlifDocument.initImagePaths` reads `Frame/@File`, falling back to `Block/@File`;
its image format is LOF, TIFF, BMP, JPEG or PNG. `XLEFReader.initFile` dispatches
only those formats and rejects unknown image formats. `LMSFileReader` is the
metadata base class, not an additional compressed-Memory pixel decoder.

Java's LOF reader reads its binary memory block and routes raw pixel bytes by
channel/tile/stride; it does not implement an XML Compression-selected codec.
Rust's optional raw-Storage metadata leaf path is extra support and its limits
must not be described as missing translation of a Java decoder.

A direct Java probe of a Memory/Storage-only XLIF reports
`valid=false, images=0, format=UNKNOWN`. The new Rust document test proves the
same behavior and confirms that a real Frame still selects TIFF regardless of
an unrelated Memory compression attribute. The Java probe also confirms OI →
Oil, W → Water, PlApo → PlanApo, and unknown → Other enum normalization.
Artifacts: `.tmp/gap-leica-oracle/`. The adapter also preserves the upstream
handler's overlapping-pattern priority: Neofluar and PlanNeofluar resolve
to Fluar in the Java dependency used by this baseline.
